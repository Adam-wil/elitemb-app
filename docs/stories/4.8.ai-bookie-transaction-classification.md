# Story 4.8: AI-Powered Bookie Transaction Classification

## Status

In Progress

## Story

**As a** matched bettor,
**I want** bank transactions automatically classified as bookie deposits/withdrawals using AI,
**So that** my ledger stays accurate without manual data entry.

## Background

The existing `bookieDetection.ts` uses fuzzy string matching with ~70% confidence threshold. While functional, it:
- Misses transactions with unusual descriptions
- Can't learn from corrections
- Struggles with payment processor intermediaries (e.g., "PAYPAL *SPORTSBET")

AI classification provides higher accuracy and can improve over time with user corrections.

## Acceptance Criteria

1. Basiq transactions are classified using AI on initial sync
2. Daily sync processes new transactions automatically
3. High-confidence matches (>90%) auto-create journal entries
4. Low-confidence matches (<90%) queued for manual review
5. User can confirm/reject/correct classifications
6. Corrections stored and used to improve future classification accuracy
7. Only bookie transactions are processed (non-bookie ignored)
8. Betfair transactions identified separately (exchange vs regular bookie)
9. Journal entries update bookie P&L displayed on Ledger performance chips
10. Transaction history visible when tapping bookie card in AccountDetailSheet
11. Fallback to fuzzy matching if AI classification unavailable
12. Correction patterns remembered and applied to similar future transactions
13. Bank institution context passed to AI to handle different description formats
14. Betfair transactions identified with `isExchange: true` flag
15. Exchange withdrawals displayed as "Profit Extraction" in UI (primary profit point)
16. Exchanges shown in separate section on Ledger tab (distinct from bookies)
17. Net profit calculation for exchanges (total withdrawn - total deposited)
18. Bookie withdrawals flagged as rare for gubbing awareness

### Chunking Strategy

| Stage | Chunk Size | Rationale |
|-------|------------|-----------|
| Basiq fetch | All at once | Basiq handles pagination internally |
| DB duplicate check | 100 | Efficient `IN` clause query |
| FTS pattern search | 1 per txn | GIN index makes this fast |
| AI classification | 10-20 | Anthropic rate limits, parallel calls |
| DB insert | 50-100 | Prisma createMany efficiency |
| Journal creation | 1 per txn | Needs individual account lookups |

**Chunk Processing with Error Handling:**
```typescript
async function processChunk(chunk: Transaction[], profileId: string) {
  const results = { success: [], failed: [], skipped: [] }

  for (const txn of chunk) {
    try {
      // 1. Skip if already classified
      const existing = await checkExisting(txn.basiqId)
      if (existing) { results.skipped.push(txn); continue }

      // 2. FTS pattern search
      const patterns = await findMatchingPatterns(profileId, txn.description)
      if (patterns.length > 0 && patterns[0].occurrences >= 3) {
        // High-confidence pattern match - skip AI
        await classifyFromPattern(txn, patterns[0])
        results.success.push(txn)
        continue
      }

      // 3. AI classification (with pattern hint if available)
      const hint = patterns.length > 0 ? patterns[0] : null
      const classification = await classifyWithAI(txn, hint)

      // 4. Store result
      await storeClassification(txn, classification)
      results.success.push(txn)

    } catch (error) {
      results.failed.push({ txn, error })
      // Continue with next - don't fail entire chunk
    }
  }

  return results
}
```

### Multi-Step AI Reasoning

The AI classification uses a 3-step reasoning chain for higher accuracy. Each step builds on the previous, allowing the AI to "think through" ambiguous transactions.

**Why multi-step?** Single-shot classification often fails on edge cases (PayPal-wrapped transactions, obscure bookie names, white-label operators). Multi-step reasoning allows the AI to systematically evaluate the transaction, achieving better accuracy at the cost of slightly longer processing time (~30 seconds per transaction is acceptable for daily sync).

### Exchange Handling (Betfair)

Betfair is fundamentally different from regular bookies in matched betting. This distinction is critical for accurate tracking.

**Why Betfair is Different:**

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                    MATCHED BETTING MONEY FLOW                                │
└─────────────────────────────────────────────────────────────────────────────┘

  Regular Bookies (Sportsbet, Ladbrokes, etc.)
  ─────────────────────────────────────────────

  Bank ──── Deposit ────▶ Bookie ──── Bet + Bonus ────▶ Profit trapped here

                              │  (triggers gubbing/account restrictions)
                              │
                              ▼

  ────────────────

         │                       │  ✅ SAFE TO WITHDRAW

         │                       │
         │                       ▼
         │               Main profit extraction point
         │
         ▼
    User's actual profit
```

**Transaction Classification Implications:**

| Bank → Betfair deposit | Funding exchange for lay bets | Normal MB activity | EXCHANGE_DEPOSIT |

```typescript
- Westpac: Prefix, e.g., "DIRECT DEBIT SPORTSBET MELBOURNE"
- NAB: "DD -" prefix, e.g., "DD - SPORTSBET AUSTRALIA"
- ANZ: Adds location, e.g., "SPORTSBET PTY LTD MELBOURNE AU"
- ING: Transfer prefix, e.g., "Transfer to SPORTSBET"
- Up/Neobanks: May truncate, e.g., "SPORTBET P"

Common wrappers to look through:
- PayPal: "PAYPAL *SPORTSBET"
- POLi: "POLI *LADBROKES"
- Bank prefixes: "DIRECT DEBIT", "DD -", "Transfer to/from"

Previous analysis determined this IS gambling-related:
{step1_reasoning}

Transaction:
Description: {description}
Amount: ${amount}
Direction: {direction}
Bank: {institution}

Identify the specific operator. If unsure, set bookieId to null but explain why.`

async function step2IdentifyBookie(
  txn: TransactionInput,
  step1Result: Step1Result,
  bookieContext: BookieContext[]
): Promise<Step2Result> {
  // Build bookie context string with IDs
  const bookieList = bookieContext
    .map(b => `- ${b.name} (id: ${b.id}): ${b.aliases.join(', ')}`)
    .join('\n')

  const prompt = STEP2_PROMPT
    .replace('{step1_reasoning}', step1Result.reasoning)
    .replace('{description}', txn.description)
    .replace('{amount}', Math.abs(txn.amount).toFixed(2))
    .replace('{direction}', txn.direction)
    .replace('{institution}', txn.institution || 'Unknown')
    + `\n\nKnown bookies in system:\n${bookieList}`

  const result = await model.generateContent({
    contents: [{ role: 'user', parts: [{ text: prompt }] }],
    generationConfig: {
      responseMimeType: 'application/json',
      responseSchema: STEP2_SCHEMA,
    },
  })

  return JSON.parse(result.response.text())
}

const STEP3_PROMPT = `You are making a final classification decision using all available context.

Previous analysis:
Step 1 (Is gambling?): {step1_reasoning}
Step 2 (Which bookie?): {step2_reasoning}
Step 2 suggested: {step2_bookie} with {step2_confidence}% confidence

User correction history for similar transactions:
{correction_patterns}

Transaction:
Description: {description}
Amount: ${amount}

Based on ALL context, make your final decision. User corrections are highly reliable -
if a similar pattern was corrected before, trust that correction.`

async function step3CrossReference(
  txn: TransactionInput,
  step1Result: Step1Result,
  step2Result: Step2Result,
  correctionPatterns: CorrectionPattern[]
): Promise<ClassificationResult> {
  const patternsText = correctionPatterns.length > 0
    ? correctionPatterns.map(p =>
        `- "${p.descriptionPattern}" → ${p.correctedBookieName} (used ${p.occurrences}x)`
      ).join('\n')
    : 'No previous corrections found for similar patterns.'

  const prompt = STEP3_PROMPT
    .replace('{step1_reasoning}', step1Result.reasoning)
    .replace('{step2_reasoning}', step2Result.reasoning)
    .replace('{step2_bookie}', step2Result.bookieName || 'Unknown')
    .replace('{step2_confidence}', (step2Result.confidence * 100).toFixed(0))
    .replace('{correction_patterns}', patternsText)
    .replace('{description}', txn.description)
    .replace('{amount}', Math.abs(txn.amount).toFixed(2))

  const result = await model.generateContent({
    contents: [{ role: 'user', parts: [{ text: prompt }] }],
    generationConfig: {
      responseMimeType: 'application/json',
      responseSchema: STEP2_SCHEMA, // Same schema as Step 2
    },
  })

  return JSON.parse(result.response.text())
}

export const classifyTransaction = createServerFn({ method: 'POST' })
  .inputValidator((input: {
    description: string
    amount: number
    direction: 'credit' | 'debit'
    institution?: string
    profileId?: string
  }) => input)
  .handler(async ({ data }): Promise<ClassificationResult> => {
    try {
      // Step 1: Is this gambling-related?
      const step1 = await step1IsGambling(data)

      if (!step1.isGambling || step1.confidence < 0.5) {
        return {
          bookieId: null,
          bookieName: null,
          isExchange: false,
          confidence: step1.confidence,
          reasoning: `Not gambling: ${step1.reasoning}`,
          status: 'IGNORED',
        }
      }

      // Get bookie context from database
      const bookies = await prisma.bookie.findMany({
        select: { id: true, name: true, aliases: true },
      })

      // Step 2: Which bookie/exchange?
      const step2 = await step2IdentifyBookie(data, step1, bookies)

      // If high confidence, skip Step 3
      if (step2.confidence >= 0.90) {
        return {
          bookieId: step2.bookieId,
          bookieName: step2.bookieName,
          isExchange: step2.isExchange,
          confidence: step2.confidence,
          reasoning: step2.reasoning,
          status: step2.confidence >= 0.90 ? 'AUTO_JOURNALED' : 'PENDING_REVIEW',
        }
      }

      // Step 3: Cross-reference with correction patterns
      const patterns = await findMatchingPatterns(data.profileId, data.description)
      const step3 = await step3CrossReference(data, step1, step2, patterns)

      return {
        bookieId: step3.bookieId,
        bookieName: step3.bookieName,
        isExchange: step3.isExchange,
        confidence: step3.confidence,
        reasoning: step3.reasoning,
        status: step3.confidence >= 0.90 ? 'AUTO_JOURNALED' : 'PENDING_REVIEW',
      }

    } catch (error) {
      // Fallback to fuzzy matching if Gemini fails
      console.error('Gemini classification failed, falling back to fuzzy:', error)
      const fuzzyResult = detectBookie(data.description)
      return {
        bookieId: fuzzyResult?.bookieId || null,
        bookieName: fuzzyResult?.bookieName || null,
        isExchange: fuzzyResult?.isExchange || false,
        confidence: fuzzyResult?.confidence || 0,
        reasoning: 'Fallback: Fuzzy matching (AI unavailable)',
        status: 'PENDING_REVIEW', // Always review fallback results
      }
    }
  })
```

### Correction Learning System with Full-Text Search

**Why FTS?** Exact matching is brittle. "ACME WAGERING SERVICES" won't match "ACME WAGERING PTY LTD". Full-text search enables fuzzy matching on key terms.

```typescript
// Find matching correction patterns using FTS
async function findMatchingPatterns(
  profileId: string,
  description: string
): Promise<CorrectionPattern[]> {
  // Convert description to tsquery (AND between words)
  // "ACME WAGERING SERVICES" → 'acme & wagering & services'
  const searchTerms = description
    .toUpperCase()
    .replace(/[^A-Z0-9\s]/g, '') // Strip special chars
    .split(/\s+/)
    .filter(word => word.length > 2) // Skip short words
    .join(' & ')

  const patterns = await prisma.$queryRaw<CorrectionPattern[]>`
    SELECT *
    FROM "CorrectionPattern"
    WHERE "profileId" = ${profileId}
      AND "searchVector" @@ to_tsquery('english', ${searchTerms})
    ORDER BY
      ts_rank("searchVector", to_tsquery('english', ${searchTerms})) DESC,
      "occurrences" DESC
    LIMIT 5
  `

  return patterns
}
```

## Decisions Made

1. **AI Provider: Gemini 2.0 Flash**: Chosen over Claude/Anthropic for cost efficiency (~$1-2/month vs ~$10+/month). Native structured output support eliminates JSON parsing issues. Fallback to existing `bookieDetection.ts` fuzzy matching if Gemini unavailable.

2. **3-Step Reasoning Chain**: Multi-step classification (Is gambling? → Which bookie? → Cross-reference) provides higher accuracy than single-shot, especially for edge cases. ~30 seconds per transaction is acceptable for daily sync workloads.

3. **Exchange Handling (Betfair)**: Betfair tracked separately from bookies because it serves a fundamentally different purpose in matched betting (profit extraction vs bonus turnover). Exchange withdrawals displayed as "Profit Extraction" to reflect their true meaning. Smarkets deferred to future release.

4. **Offline Strategy**: Fallback to fuzzy matching if AI unavailable. Edge case since matched betting requires being online to place bets.

5. **API Cost Management**: Not a concern during dev/testing phase (1-2 users). Correction patterns will reduce API calls over time as common descriptions are learned.

6. **Learning from Corrections**: Essential for user experience. Patterns stored per-profile, can inform prompt improvements and potentially feed into other AI features (e.g., bet categorization, anomaly detection) in future.
